# 7.2.4 发布验证变更草案

状态：待用户确认。当前正式版仍为 7.2.3，尚未切换 main 或发布 7.2.4。故障机的服务端定向恢复已由用户回报完成。

## 为什么需要变更

原 `.github/workflows/vps-stability.yml` 在每次 main push 时通过 SSH 操作三台测试 VPS。用户已删除这些机器，不能继续连接。现有发布器和两类 7.2.1 旧更新器同时要求 `ci.yml` 与 `vps-stability.yml` 在同一个 main SHA 上有最新且完整的 push 成功记录。当前不能用单机恢复回执冒充原来的三机测试。

## 提议采用的检查

1. 对待发布提交运行完整 CI，包括 Debian 12、Ubuntu 22.04、Ubuntu 24.04 容器检查、现有回归及发布包校验。移除工作流改动复用父提交 CI 结果的路径。
2. 将 `vps-stability.yml` 的执行内容和显示名改为 `Release recovery evidence`：读取真实用户回执，验证其结构和范围，并核对被执行 helper、两个修复模块、目标候选包的实际摘要。工作流不会连接任何 VPS；日志必须明确它验证的是用户回执的一致性。
3. 新门禁必须使用 `--require-approved-policy`。回执方案当前标记为 `proposal-awaiting-owner-confirmation`，正式门禁会拒绝；用户明确确认后才能记录 `owner-approved` 并切换 main。
4. 旧 `vps-audit.yml` 与 `cross-os-management.yml` 移出活动工作流目录，保留为历史归档，避免后续手动任务连接退役机器。

工作流路径继续保留是为了让已安装的 7.2.1 更新器认识新的发布结果；这不表示旧的三机检查已经运行。显示名、更新日志和发布报告都声明验证范围变化。

## 发布及旧热更新要求

确认方案后，最终 main 提交必须重新通过两个真实发布门禁。发布器仍独立核对 main、最新 push 运行、annotated tag 所有权、immutable Release 和全部摘要；不删除检查，不使用 workflow_dispatch 替代 push 证据，不复用其它 SHA 的结果。

用户确认的执行范围包含：记录已批准状态、完成正式版文案并合并最终提交；该 main 提交的两个门禁都成功后，现有发布调度器会自动触发 7.2.4 正式发布。草案 PR 本身不会执行这一步。

正式 Release 必须保留恰好五项资产：`install.sh`、`manifest.sha256`、`rr-bundle.tar.gz`、`RELEASE_INFO`、`SHA256SUMS`。旧更新器还要求 Latest、Tag 和 main 指向相同提交，发布后不得再追加同版本的 main 文档提交造成不一致。发布完成后需读取实际远端结果再次核对；此次提议没有访问或修改两台主力服务器。
